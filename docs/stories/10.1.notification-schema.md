## Contexto

O Epic 10 dá a cada usuário um número WhatsApp verificado + escolha de
**quais impressoras** e **quais eventos** recebe. Hoje não existe
nenhuma tabela de notificação normalizada — só uma coluna solta
`users.notificationChannels` jsonb `{ telegramChatId?, email? }`
(legado, usada pelo Telegram global). Esta story cria **apenas o
schema** que as stories 10.2-10.6 vão consumir.

**Decisão de compatibilidade:** a coluna `users.notificationChannels`
**NÃO é alterada nem removida** nesta story (algo pode lê-la; o Telegram
global continua intocado por decisão do Epic). As novas tabelas são
**aditivas**. Deprecação/migração da coluna legada é fora de escopo
(possível V1.1).

## Acceptance Criteria

### Tabela `notification_channels`

1. Criar tabela `notification_channels` com colunas:
   - `id` uuid PK `defaultRandom()`
   - `user_id` uuid NOT NULL → FK `users.id` `onDelete: 'cascade'`
   - `type` enum `notification_channel_type` com valor inicial `'whatsapp'` (enum criado de forma extensível — futuros `'telegram'`, `'email'` sem migration destrutiva)
   - `destination` text NOT NULL (número E.164, ex: `+5514XXXXXXXXX`)
   - `verified` boolean NOT NULL default `false`
   - `verified_at` timestamptz NULL
   - `code_hash` text NULL (hash do código de verificação — nunca o código cru)
   - `code_expires_at` timestamptz NULL
   - `created_at` timestamptz NOT NULL `defaultNow()`
   - `updated_at` timestamptz NOT NULL `defaultNow()`
2. Constraint `unique(user_id, type, destination)` (um número por tipo por user) — nomear `uq_notification_channels_user_type_dest`.
3. Index em `user_id`.

### Tabela `notification_rules`

4. Criar tabela `notification_rules` com colunas:
   - `id` uuid PK `defaultRandom()`
   - `user_id` uuid NOT NULL → FK `users.id` `onDelete: 'cascade'`
   - `channel_id` uuid NOT NULL → FK `notification_channels.id` `onDelete: 'cascade'`
   - `printer_id` uuid **NULL** → FK `printers.id` `onDelete: 'cascade'` — **NULL significa "todas as impressoras da org do user"** (cobre impressoras adicionadas no futuro)
   - `event_types` text[] NOT NULL (subconjunto de `print_finished | print_failed | hms_critical | printer_offline`)
   - `active` boolean NOT NULL default `true`
   - `created_at` / `updated_at` timestamptz NOT NULL `defaultNow()`
5. Index em `printer_id` e em `user_id` (caminho de resolução de destinatários da Story 10.4).

### Migration & integridade

6. Migration SQL criada em `packages/db/migrations/0016_notification_schema.sql` seguindo a convenção numerada existente (próxima = 0016).
7. Schema Drizzle atualizado em `packages/db/src/schema.ts` (tabelas + enum + tipos exportados), seguindo os padrões do arquivo (uuid `.defaultRandom()`, `timestamp({ withTimezone: true })`, `unique().on()`, `pgEnum`).
8. Migration aplica limpo num banco com o schema atual; **nenhuma tabela/coluna existente é alterada destrutivamente** (inclui `users.notificationChannels` intacta).
9. `pnpm --filter @printstudio/db typecheck` (ou typecheck root) passa com os novos tipos exportados.

## Dev Notes

- **Padrões do schema.ts:** seguir os existentes — uuid `.primaryKey().defaultRandom()`, FK `.references(() => x.id, { onDelete: 'cascade' })`, `timestamp('col', { withTimezone: true }).defaultNow().notNull()`, `unique('nome').on(t.a, t.b)`, enums via `pgEnum`. Ver `organizationMembers`/`printers` como referência.
- **Bug conhecido de migration (padrão estabelecido):** o projeto tem o issue "Drizzle migration idx > lastId silencioso". Padrão já usado nas stories 8-9: aplicar o SQL direto via script ad-hoc + `INSERT` manual em `__drizzle_migrations`. @dev deve seguir esse padrão ao aplicar a 0016, não confiar só no `drizzle-kit migrate`.
- **`printer_id` NULL = todas:** intencional — resolve o caso "adicionei impressora nova e regra não pega". A query de resolução (Story 10.4) fará `printer_id = :id OR printer_id IS NULL`.
- **Encriptação do número:** o projeto já encripta tokens Bambu (AES-256-GCM, `bambuCredentials`). O número é o próprio do user (sensibilidade menor que token). **@data-engineer decide nesta story:** E.164 plain (simples, V1) vs encriptado. Documentar a decisão no QA Results / Dev Agent Record. Se plain, garantir que nunca vai pra log (mascarar).
- **`event_types` como text[]:** array nativo Postgres (não jsonb) pra permitir índice GIN futuro e filtro `= ANY`. Validação do conteúdo (enum dos 4) fica na camada de aplicação (Zod) nas stories 10.4/10.6 — schema não precisa de check constraint V1.
- **Não** criar seed nem dados de teste aqui. Número de teste do Richard **nunca** vai pro repo/migration.

## Dev Agent Record

**Agent Model Used:** claude-opus-4-7[1m] (@data-engineer Dara)

### Decisões registradas

- **Encriptação `destination`:** texto plano E.164. Justificativa: não é
  credencial; `UNIQUE(user_id,type,destination)` exige valor comparável;
  decrypt em todo dispatch (10.4) é custo sem benefício proporcional.
  Mitigação: nunca logar número cheio (app mascara), acesso só no escopo
  do user autenticado. Reavaliar se compliance exigir (V1.1).
- **Índices na migration, não no `schema.ts`:** segue o padrão existente
  (`adminAuditLog`/`onboardingEvents` não declaram `index()` no schema —
  `index` nem é importado). Consistência > divergência.
- **`event_types` text[]:** `text('event_types').array()` no Drizzle.
  Validação do conteúdo (os 4 valores) fica na app (Zod, 10.4/10.6).
- **Meta journal NÃO tocado:** `migrations/meta/_journal.json` para em
  idx 15 e já tem gaps (0013-0015 sem snapshot) — projeto aplica via
  ad-hoc, não `drizzle-kit migrate`. Fabricar snapshot faria mal.

### Pendência de aplicação (handoff @devops/autorização)

rodar SQL direto no DB → `INSERT INTO __drizzle_migrations` manual

(DB prod compartilhado).
