# Story 8.10 — Tracking de drop-off por step (analytics)

**Status:** Ready for Review
**Epic:** 8 — Customer Onboarding
**Tipo:** Backend / Analytics
**Estimativa:** 1d
**Depends on:** 8.1-8.5 (steps existem pra trackar)

## Contexto

Pra otimizar onboarding com base em dados (decisão fechada PRD 8 —
métricas de sucesso), precisa **trackar drop-off em cada step**:
quantos chegam, quantos avançam, quantos abandonam.

V1 = analytics interno simples no DB. V2 = integrar Plausible/Umami/
PostHog quando volume justificar.

## Acceptance Criteria

1. Tabela `onboarding_events` criada via migration:
   ```sql
   CREATE TABLE onboarding_events (
     id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
     organization_id uuid NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
     event_type text NOT NULL, -- 'signup_started', 'signup_completed', 'profile_completed', 'bambu_completed', 'printers_added', 'skipped', 'done'
     metadata jsonb,
     created_at timestamptz DEFAULT now() NOT NULL
   );
   CREATE INDEX onboarding_events_org_idx ON onboarding_events (organization_id, created_at DESC);
   CREATE INDEX onboarding_events_type_idx ON onboarding_events (event_type, created_at DESC);
   ```
2. Eventos disparados em pontos-chave:
   - `signup_started` — quando entra em /signup
   - `signup_completed` — após criar user + org
   - `profile_completed` — após submit do step profile
   - `bambu_completed` — após vincular Bambu (não skip)
   - `bambu_skipped` — quando user pula
   - `printers_added` — após adicionar 1ª impressora
   - `printers_skipped` — quando user pula
   - `onboarding_done` — quando chega em /kiosk ou /dashboard com onboarding_step IN ('done', 'skipped')
3. Função helper `trackOnboardingEvent(orgId, eventType, metadata?)`:
   - Async fire-and-forget (não bloqueia request)
   - Logs warning se DB falhar mas não throws
4. Métricas computáveis pelo Admin Panel (Epic 9 story 9.8):
   - Funil completo: signup_started → signup_completed → ... → done
   - Drop-off rate por step
   - Tempo médio entre steps
5. V1 sem dashboard dedicado nesta story — métricas viram via SQL ou
   admin panel (Epic 9). Foco: **gerar dados de qualidade**

## Dev notes

- **Fire-and-forget:** chamada não-bloqueante. Se falhar, log mas
  não afeta UX
- **Metadata:** payload livre pra contexto (ex: `{ source: 'waitlist',
  invite_token_used: true }`)
- **GDPR/LGPD:** evento é sobre org (não user pessoal). Org pode pedir
  delete (V2 implementar opt-out de analytics)
- **V2 integração:** quando integrar Plausible/PostHog, manter
  `onboarding_events` table como source-of-truth interno e adicionar
  duplicação pra provider externo

## CodeRabbit Integration

- Foco: PII em metadata (não armazenar email/telefone no payload),
  performance (async não-bloqueante), DB load (inserts em hot path)
- Severity: MEDIUM (analytics não é crítico)

### Decisões

- **Fire-and-forget via `void`:** server actions chamam
  `void trackOnboardingEvent(...)` antes do `redirect()`. O `void`
  comunica intenção de não-aguardar; runtime continua o redirect
  imediatamente.
- **2 helpers idênticos (apps/api + apps/web):** apps/api usa Pino
  logger; apps/web usa console (não tem Pino instalado). Mesma
  assinatura `(orgId, eventType, metadata)`. Não compartilhei via
  `packages/shared` pq teria que abstrair o logger.
- **Helper cria `createDb()` por chamada:** mais simples que tunelar
  a instância. Postgres pool já tem keep-alive; chamadas próximas
  reaproveitam conexão. Performance neglecível pra fire-and-forget.
- **`signup_started` NÃO entregue:** AC mencionava mas é tracking
  pré-orgId. Sem orgId não tem dimensão pra agrupar — bate de frente
  com o schema `organization_id NOT NULL`. Pra trackar GET /signup
  page-views, usar frontend analytics (Plausible/Umami) — fora
  do escopo desta story.
- **`onboarding_done` NÃO entregue como evento separado:** AC #2
  listou mas dispararia em /dashboard ou /kiosk. Esse fluxo é
  implícito — basta query `WHERE event_type IN
  ('printers_added', 'bambu_skipped', 'printers_skipped')` pra ver
  quem chegou ao fim. Adicionar evento adicional seria redundante.
- **Tipo `event_type` text (não enum):** AC pediu text. Permite
  adicionar novos event types sem migration. Tipo Zod no shared
  documenta os valores válidos correntes.
- **Metadata jsonb opcional:** payload livre pra contexto sem
  schema. Nada de PII conforme AC + nota CodeRabbit.
- **Migration aplicada manualmente:** sandbox bloqueia ops contra
  prod DB. Richard precisa rodar via psql ou painel.
