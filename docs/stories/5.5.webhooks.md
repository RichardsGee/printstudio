# Story 5.5 — Webhooks (notificações HTTP)

**Status:** Draft
**Epic:** 5 — Polish & UX
**Tipo:** Backend (API + Worker)
**Estimativa:** 2-3 dias

**Prioridade:** P3 (futuro, fazer depois de 5.1-5.4 e Epic 6)

## Contexto

Cliente precisa receber notificações em sistemas externos: Slack quando
print termina, Discord quando dá erro, planilha automatizada via Zapier,
ERP próprio do cliente. Em vez de cada integração ser custom, expor um
sistema de webhooks genérico.

## Acceptance Criteria

1. Schema: tabela `webhooks` com colunas:
   - `id`, `org_id`, `url`, `secret`, `events[]` (array de strings),
     `enabled`, `created_at`, `last_delivery_at`, `last_status`
2. UI: página de configurações da org → seção "Webhooks"
   - CRUD básico (criar, listar, editar, deletar)
   - Botão "testar" envia POST de teste
3. Eventos suportados (V1):
   - `print.started`
   - `print.finished`
   - `print.failed`
   - `print.paused`
   - `printer.offline`
   - `printer.online`
4. Entrega: POST JSON com `event`, `timestamp`, `printer`, `data`
5. Assinatura HMAC-SHA256 no header `X-PrintStudio-Signature`
6. Retry: 3 tentativas com backoff exponencial (1s, 10s, 60s)
7. Dead letter: após 3 falhas, marca webhook com `last_status='failed'`
   e desabilita após 10 falhas consecutivas
8. Log de entregas (últimas 100 por webhook) acessível na UI

## Non-Goals

- Subscriptions GraphQL ou WebSocket externo
- Configuração de retries por webhook (fixo no V1)
- Templates customizáveis de payload

## Arquivos prováveis

- `packages/db/src/schema.ts` — tabela `webhooks` + `webhook_deliveries`
- `apps/api/src/routes/webhooks.ts` — CRUD
- `apps/api/src/services/webhook-dispatcher.ts` — envio + retry
- Trigger: evento de mudança de estado no PrinterState (ver onde é
  detectado hoje no api/worker)
- `apps/web/src/app/(app)/settings/webhooks/...`

## Dev notes

- Eventos detectados no api (não no worker) pra consolidar source-of-truth
- Worker já manda PrinterState pelo WS — api compara estado anterior
  e dispara evento se for transição relevante
- Considerar fila persistente (BullMQ + Redis) se volume crescer.
  V1 pode ser in-memory queue + retry sync.
