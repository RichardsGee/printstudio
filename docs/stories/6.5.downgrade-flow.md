# Story 6.5 — Downgrade flow (handle quando exceder limits novo plano)

**Status:** Ready
**Epic:** 6 — Pagamentos & Monetização
**Tipo:** Backend + Frontend
**Estimativa:** 1d
**Depends on:** 6.2 (subscriptions schema), 6.3 (UI billing)

## Contexto

Quando user no Pro/Business faz downgrade pra plano menor (ou cancela
pra free), pode ter **excedido limits** do novo plano. Ex: 5 impressoras
no Pro → free só permite 1.

Decisão fechada PRD 6: **não soft-delete imediato**. Bloqueia uso de
impressoras excedentes mas preserva dados 90d, depois soft-delete.

## Acceptance Criteria

1. Server action `downgradePlan(orgId, newPlan)`:
   - Valida exceeding limits via `lib/plan-limits.ts`
   - Atualiza `subscriptions.plan = newPlan` + `cancel_at_period_end = true`
     se for cancelamento
   - **Não deleta** printers excedentes. Marca-as como `archived = true`
2. Schema additions:
   ```sql
   ALTER TABLE printers ADD COLUMN archived boolean DEFAULT false NOT NULL;
   ALTER TABLE printers ADD COLUMN archived_at timestamptz;
   ```
3. **Warning modal** antes de confirmar downgrade:
   - "Você tem 5 impressoras. Plano Free permite 1."
   - "As impressoras excedentes serão arquivadas (não removidas) por 90d"
   - "Você pode voltar pra Pro e reativá-las a qualquer momento"
   - `[Confirmar downgrade]` `[Cancelar]`
4. Após downgrade:
   - User precisa **escolher qual impressora manter ativa** (UI list
     com radio button)
   - As demais são marcadas archived
   - Banner persistente no app: "Você tem X impressoras arquivadas.
     [Upgrade pra reativar →]"
5. **Cron de cleanup** (worker job):
   - 1x/dia verifica `archived_at < NOW() - INTERVAL '90 days'`
   - Soft-delete (`printers.deleted_at = now()`) — não DROP
   - Email/notificação ao owner (V2)
6. Endpoints de printers filtram archived por default (mas admin
   panel mostra)

## Dev notes

- **Archived vs deleted:** archived = reversível 90d, deleted = hard
  delete (queryable só pelo admin)
- **Decision flow:** User clica "Downgrade" → modal warning → server
  action que cria pending downgrade → quando subscription period ends,
  webhook efetiva
- **Imediato vs scheduled:** V1 = scheduled (downgrade efetiva no fim
  do ciclo pago). V2 = imediato com pro-rata refund
- **Multi-user impact:** quando max_users excedido, owner é mantido,
  members extras viram convidados read-only? V2
