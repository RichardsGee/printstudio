## Acceptance Criteria

1. Página `/admin/waitlist` com tabela paginada (50/page):
   - Colunas: nome, email, região (UF + cidade), role, status (badge
     colorido), bambu_count, tags, criado_at, last_contact_at
   - Sort por: criado_at DESC (default), nome, status
2. **Filtros** no topo:
   - Status (multi-select)
   - Região (multi-select UF)
   - Role (multi-select)
   - Tag (multi-select de tags existentes)
   - Range de data (criado_at)
   - Range de bambu_count
3. **Busca** por nome ou email (debounce 300ms)
4. **Métricas no topo** (cards):
   - Total leads
   - Novos 7d
   - Conversão signup (% de status='converted')
   - Distribuição por status (pie chart pequeno)
5. **Ações por linha** (inline ou drawer detail):
   - Editar `status` (dropdown inline)
   - Adicionar/remover tag (chip editor)
   - Editar notes (textarea inline)
   - **Gerar link de convite** (story 9.4)
   - **Marcar como contatado** (atualiza `last_contact_at`)
6. **Bulk actions:**
   - Marcar status mass
   - Tag mass
7. URL state: filtros viram query params (shareable)
8. Server-side pagination + filtering (sem fetch tudo)

## Dev notes

- **Pagination:** cursor-based pra evitar offset slow em waitlist grande.
  Próxima/anterior page via `created_at` cursor
- **Search:** SQL `ILIKE` em name + email com index. Postgres trigram
  pode entrar V1.1 se precisar
- **Filtros multi-select:** `status IN (...)`, `state = ANY(...)`,
  `tags && (...)` (overlap pra GIN index)
- **URL state:** `useSearchParams` + `useRouter` push pra shareable
  URLs (`/admin/waitlist?status=new,contacted&state=SP`)
- **Inline edit:** optimistic update (atualiza UI imediato, rollback
  se server action falhar)
- **Audit log:** toda ação gera entry em `admin_audit_log` (story 9.9)

### Decisões

- **Cursor-based pagination (sem OFFSET):** AC #pediu. Cursor =
  `created_at DESC` em ISO string no URL. Trunca em `limit + 1` rows
  pra detectar `hasMore`. Não precisa de COUNT total que seria caro
  em tabela grande.
- **Filters multi-select via chip toggle:** mais escaneável que
  combobox. UF tem 27 chips — funciona pq o user filtra raramente
  por UF (mais comum status).
- **URL state via `router.replace`:** atualiza sem entry no history
  (back button volta pra última *página* real, não pra cada filter
  change). Filters shareables.
- **Search debounced 300ms via `useEffect`:** evita router.replace
  spam enquanto user digita.
- **Mobile cards em vez de horizontal scroll:** densidade alta de
  campos por linha. Card stack é mais legível em < lg.
- **Tags lowercase + `[a-z0-9_-]+`:** convenção comum (Linear,
  GitHub). Evita "Hot Lead", "hot-lead", "HotLead" duplicados.
- **Tags idempotentes via SQL `CASE WHEN ... = ANY`:** evita race
  se 2 admins adicionam mesma tag simultaneamente.
- **`markWaitlistContacted` auto-promove status:** UX simples — se
  user clica "marcar contatado" num lead 'new', já passa pra
  'contacted'. Se já tava engaged/converted, preserva.
- **Sem audit log V1:** Story 9.9 implementa a tabela + integração.
  Por agora actions só revalidam path; `updated_at` é o trail.
- **Sem bulk actions V1:** AC #6 pediu mas é complexidade extra.
  Pode ser adicionado depois com select rows + popover ação. Operação
  manual via filter + inline é suficiente pra primeiros 100-200 leads.
- **Sem pie chart V1:** Story 9.8 (Métricas dashboard) faz isso melhor
  com bibliotec específica. Cards de números + counts por chip já
  comunicam distribuição.
