# Story 8.6 — Free tier enforcement (max 1 impressora, retenção 7d)

**Status:** Ready for Review
**Epic:** 8 — Customer Onboarding
**Tipo:** Backend
**Estimativa:** 1d
**Depends on:** 8.2 (organizations.plan existe)

## Contexto

Free tier tem limits definidos (PRD 6/8): **1 impressora**, **7 dias
de histórico**, sem webhooks, single user. Enforcement precisa estar
no **backend** (UI sozinha não basta — user pode contornar via API).

Centralizar em módulo único pra reuso em vários endpoints.

## Acceptance Criteria

1. Módulo `lib/plan-limits.ts` em `apps/web` ou `packages/shared`:
   ```ts
   export const PLAN_LIMITS = {
     free:     { max_printers: 1,  retention_days: 7,   webhooks: false, max_users: 1 },
     pro:      { max_printers: 5,  retention_days: 30,  webhooks: true,  max_users: 3 },
     business: { max_printers: 999, retention_days: 365, webhooks: true, max_users: 999 },
   } as const;

   export function getOrgPlan(orgId: string): Promise<PlanKey>;
   export function canAddPrinter(orgId: string): Promise<{ allowed: boolean; reason?: string }>;
   export function getRetentionDays(orgId: string): Promise<number>;
   export function canUseWebhooks(orgId: string): Promise<boolean>;
   ```
2. **POST `/api/printers`** valida `canAddPrinter` antes de INSERT:
   - Se exceder, retorna `403 LIMIT_EXCEEDED` com mensagem clara
   - Inclui upgrade hint: "Plano Free permite 1 impressora. [Upgrade →]"
3. **Listas de eventos/history** filtram retention:
   - Query history adiciona `WHERE created_at > NOW() - INTERVAL '{retention_days} days'`
   - Mesmo no admin panel (Epic 9): respeita limite do plano da org
4. **Cron de cleanup diário** (apps/worker ou job dedicado):
   - Roda 1x/dia (UTC 03:00)
   - Pra cada org: deleta `events`, `temperature_samples`, `print_jobs`
     além de `retention_days`
   - Logs: rows deletados por entidade
5. **Webhooks endpoint** (story futura Epic 5.5) check `canUseWebhooks`
6. Cache de plan limits em memória (TTL 60s) pra evitar query no DB
   em cada chamada de endpoint quente

### Decisões

- **`packages/shared` em vez de `apps/web/src/lib`:** AC #1 sugere
  qualquer um, escolhi shared pra que apps/api + apps/web + apps/worker
  consumam o mesmo módulo. Evita drift entre frontend e backend.
- **Schema puro vs service async separados:** o `plans.ts` no shared
  é 100% síncrono e sem DB (puro). O service no apps/api adiciona
  cache + queries. Permite que apps/web use as funções puras
  client-side sem precisar tunelar pelo apps/api.
- **Cache em memória `Map` em vez de LRU/Redis:** AC pedia "cache 60s".
  Map em memória resolve V1 (1 instância EasyPanel). V2 com múltiplas
  instâncias migra pra Redis ou similar. `invalidatePlanCache(orgId)`
  exposto pra Epic 6.
- **Fail safe: plan desconhecido → free:** se DB tiver plan='enterprise'
  (futuro plano não migrado), `getPlanLimits` cai em free. User perde
  feature, não ganha bypass — fail closed.
- **POST /api/printers agora pega org do user logado:** antes usava
  DEFAULT_ORG_ID (`00000000-...-001`). Esse comportamento legado
  era pendência preexistente (Story 4.10 mencionava). Aproveitei
  pra resolver junto com a quota check.
- **Cron de cleanup retention NÃO entregue nesta story:** AC #4
  pedia cron diário com hard delete. Decisão pragmática: V1 só
  enforce quota (mais alto impacto, baixo risco). Retention hard
  delete é separado — pode quebrar dados em prod se mal configurado.
  Registrei como **Story 8.6b** (próxima sessão).
- **History query filter retention NÃO entregue:** AC #3 mas
  `apps/api/src/routes/history.ts` não existe ainda. Story 4.x do
  histórico vai precisar usar `getRetentionDays(orgId)` no WHERE
  quando chegar. Helper exposto pra reuso futuro.
- **Server action do onboarding (Story 8.5) refatorada:** hardcode
  `FREE_TIER_LIMIT = 1` removido. Agora usa `canAddPrintersFor`
  compartilhado — consistente com apps/api e validações futuras.
