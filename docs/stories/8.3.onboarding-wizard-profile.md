# Story 8.3 — Onboarding wizard step 1 — perfil (org name + estado + cidade + role)

**Status:** Ready for Review
**Epic:** 8 — Customer Onboarding
**Tipo:** Frontend
**Estimativa:** 1d
**Depends on:** 8.2 (org existe com onboarding_step = 'profile')

## Contexto

Primeiro step do wizard pós-signup. User completa **perfil da
organização** (nome editável, região, role) antes de prosseguir pra
Bambu Connect.

Se veio de waitlist (story 8.9), campos pre-fillados. Senão, brancos
com placeholder.

## Acceptance Criteria

1. Página `/onboarding/profile` em `apps/web/src/app/onboarding/profile/page.tsx`
2. Server component verifica `session` + `org.onboarding_step`:
   - Se não logado → redirect `/login`
   - Se `onboarding_step != 'profile'` → redirect step atual (`/onboarding/{step}` ou `/dashboard` se done)
3. Form com campos:
   - **Nome da organização*** (text, pre-fill "Org de {primeiro nome}")
   - **Estado*** (dropdown 27 UFs BR)
   - **Cidade** (text opcional)
   - **Qual seu uso?*** (dropdown role: hobbyist / small_shop / studio / business / other)
4. Pre-fill se `org.waitlist_id != null`:
   - Busca `waitlist` linked → carrega state/city/role
5. Submit `[Próximo]`:
   - Server action `updateOrgProfile` valida + atualiza
   - Atualiza `organizations.onboarding_step = 'bambu_connect'`
   - Redirect `/onboarding/bambu-connect`
6. Layout: PageHeader `id="ONBOARDING-1/3"`, título "Conta a gente um pouco"
7. **Progress indicator** no topo: `[●] Perfil → [○] Bambu → [○] Impressoras`
8. **Sem botão "Pular"** neste step (perfil é obrigatório)

### Decisões

- **`/onboarding` fora do `(app)` group:** AC sugeria layout próprio
  do wizard (sem `AppHeader`). Movimentei a rota inteira pra raiz.
  Layout do wizard tem header minimal (logo + nome da org).
- **State machine no layout, não no middleware:** validação de step
  vive no `OnboardingLayout` Server Component em vez de middleware
  Next porque ele já precisa carregar a org pro header — evita
  consulta dupla.
- **`requireCurrentOrg` retorna summary completo:** estendi o helper
  existente `requireCurrentOrgId` em vez de fazer query separada.
  Cobertura: 9 campos da `organizations` que o wizard precisa.
- **Pre-fill prioriza dados já gravados na org:** se user voltar pro
  step (ex: editar antes de bambu-connect), os campos vêm preenchidos
  com o que já salvou. Só cai no waitlist linked se algum campo está
  vazio na org.
- **`redirect()` fora do try/catch:** Next.js `redirect()` lança
  `NEXT_REDIRECT` error que precisa propagar pro framework. Capturar
  num catch genérico quebraria o redirect.
- **Validação dupla (Zod client + Zod server):** schema é o mesmo
  (`OrgProfileSchema` de `@printstudio/shared`). Client roda pra
  feedback rápido; server revalida pra segurança contra replay.
- **Submit como `Promise` na server action:** retorna `UpdateOrgProfileResult`
  pra UI mostrar erro inline. Em sucesso, `redirect()` lança e a
  branch não retorna — o client trata `result && !result.ok`
  defensivamente.
- **HTML nativo > Radix Select:** mesmo pattern já validado no
  apps/marketing (Story 7.2). Acessível por default, sem peso.
- **Layout valida step via headers `x-invoke-path` / `x-pathname`:**
  ainda há divergência entre versões do Next 15 sobre qual header
  carrega o path atual. Tento 3 headers e só redireciono se tiver
  certeza — fail open evita loop de redirect.
